# SY-22 Research: DeepSeek V4 Pro Reasoning Model Support

## Resolved Questions

The PRD's open questions were either **resolved during PRD review** (Decisions section) or **explicitly deferred / non-blocking**. The user invoked research with an explicit "no clarifying questions" directive, so the deferred questions remain deferred and the resolved decisions stand verbatim from the PRD:

- **Q:** Should `reasoning_effort` auto-escalate to `"max"` when MCP is configured? · **A:** Yes — auto-escalate when `config.mcp.is_some()` AND user did not set `reasoning_effort`. Explicit user values always win. (PRD Decisions §1, Goal 3, Scenario 22.3 step 3.)
- **Q:** What is the policy for `reasoning_content` in conversation history replay? · **A:** Drop on text-only turns; keep on tool-call turns. DeepSeek-spec exact, no config knob. (PRD Decisions §2, Goal 6, Scenario 22.2 step 2.)
- **Q:** Default visibility of reasoning to humans? · **A:** CLI on (`cli.show_reasoning = true`); Telegram off (`telegram.show_reasoning = false`). Privacy-preserving in Telegram because messages can be screenshotted/forwarded. (PRD Decisions §3, Scenarios 22.6 / 22.7.)
- **Q:** Add a `/reasoning` runtime toggle in Telegram? · **A:** No — config-driven only in SY-22; per-chat runtime toggling deferred to a follow-up. (PRD Decisions §4, Scenario 22.7 step 4.)

Deferred (do **not** block this ticket; defaults documented in PRD):

1. Auto-raising `max_tokens` floor when `reasoning_effort = "max"` is set with a low cap → document recommendation only; revisit if practice shows truncation.
2. Anthropic / OpenAI extended-thinking adoption → separate follow-up (proposed SY-23). SY-22 establishes the `Message.reasoning_content` + `StreamEvent::ReasoningDelta` contract those providers can adopt later.

## Patterns in Use

1. **Thin-wrapper providers over `OpenAiCompatProvider`** (SY-21 consolidation). `DeepSeekProvider(pub(super) OpenAiCompatProvider)` and `OpenAiProvider(pub(super) OpenAiCompatProvider)` are both ~70 lines. SY-22 extends the inner struct with a new `Option<ReasoningSettings>` field and **only** the DeepSeek wrapper passes a `Some` for reasoning-capable models. The OpenAI wrapper never sets it, guaranteeing zero wire-format change for OpenAI traffic. This is the same pattern that allowed `tool_choice` to be DeepSeek-aware without touching OpenAI calls.
2. **`#[serde(skip_serializing_if = "Option::is_none")]` on optional request fields.** Already used on `ApiRequest::tools`, `ApiRequest::tool_choice`, and `ApiMessage::content/tool_calls/tool_call_id`. New `thinking`, `reasoning_effort`, `ApiMessage.reasoning_content` follow the same pattern — produces byte-identical wire format vs. today when the option is `None`.
3. **`#[serde(default)]` on optional response fields.** Already used on `ChoiceMessage::content` and `StreamChoice::finish_reason`. New `ChoiceMessage.reasoning_content` and `StreamDelta.reasoning_content` follow this pattern — robust to providers that omit the field.
4. **Environment-variable serialization in factory tests.** `ENV_MUTEX: Mutex<()>` in `synapse-core/src/provider/factory.rs:115`. Reasoning-effort tests that mutate `DEEPSEEK_API_KEY` must reuse the same mutex pattern (or use `make_config(...)` and avoid env mutation if possible — the factory already supports config-only API keys).
5. **Free-function serde defaults.** `default_max_tokens()`, `default_max_sessions_per_chat()`, etc. The new `[cli] show_reasoning` default uses `default_cli_show_reasoning() -> bool { true }`; `telegram.show_reasoning` default uses `default_telegram_show_reasoning() -> bool { false }`. Consistent with existing config-defaults pattern; manual `Default` impl on `TelegramConfig` must be updated (it does **not** derive — see `synapse-core/src/config.rs:163`).
6. **`tracing` structured events in factories.** `tracing::info!(provider = %config.provider, model = %config.model, "factory: creating provider")` already in factory.rs:55. Add a sibling `tracing::info!(model, effort, auto_escalated, "factory: enabling DeepSeek thinking mode")` when reasoning is enabled.
7. **Migrations: timestamp-prefixed SQL files in `synapse-core/migrations/`.** Three exist (`20250125_001_initial.sql`, `20260208_002_add_tool_columns.sql`, `20260226_003_drop_system_prompt.sql`). The tool-columns migration is the precedent: `ALTER TABLE messages ADD COLUMN <name> TEXT;` — nullable, no default. SY-22 follows that exact pattern with `20260510_004_add_reasoning_content.sql`. `sqlx` tracks applied migrations in `_sqlx_migrations` so re-running is a no-op.
8. **Char-safe truncation via `synapse_core::text::truncate`.** Single source for ellipsis-on-overflow truncation. Telegram-side reasoning preview truncation must reuse it (UTF-8 boundary safety; SY-21 made it the project default).
9. **`build_api_messages` as the wire-format adapter.** Currently maps `Message → ApiMessage` 1:1 with `tool_calls`, `tool_call_id`, `content`. Adding `reasoning_content` here is the right place; the gating logic (`m.tool_calls.is_some() && m.reasoning_content.is_some()`) lives in this function. No need to change `Agent`'s message handling — the agent already pushes the full `Message` (including reasoning) to history.
10. **Streaming via `async_stream::stream!` + `eventsource-stream`.** `stream_sse` parses SSE chunks via `serde_json::from_str::<StreamChunk>`. Adding `reasoning_content` to `StreamDelta` and a `StreamEvent::ReasoningDelta(String)` yield path mirrors the existing `TextDelta` path one-for-one. The `[DONE]` sentinel handling is unchanged.
11. **Two-channel UI rendering.** REPL renders in `Style::default().add_modifier(Modifier::DIM | Modifier::ITALIC)` — `ratatui` already imports `Modifier` in `render.rs`. Telegram uses `<blockquote>` from the supported HTML subset (`format.rs` line 33 lists `blockquote` as supported). Both use existing styling primitives — no new dependencies.

## Limitations & Risks

- **`Message` is a public struct with public fields.** Adding `reasoning_content` is additive but breaks any existing struct-literal `Message { role, content, tool_calls, tool_call_id }` outside `synapse-core`. Codebase audit (`ast-index usages "Message"`) shows struct-literal initialization is internal-only (tests and `provider/openai_compat.rs::complete_request`); all interface crates use `Message::new(...)` or `Message::tool_result(...)`. **No external break expected**, but tests must be audited; semver pre-1.0 covers this.
- **`StreamEvent` is `#[derive(Debug, Clone)]`** but **not** `#[non_exhaustive]`. Adding `ReasoningDelta(String)` is technically a breaking change for any external `match` exhaustiveness consumer. Internal `match`es in REPL and one-shot CLI must be updated; library has no external consumers (`synapse-core` is workspace-internal). Pre-1.0 covers this.
- **`MockProvider` does not currently support reasoning content.** Agent integration tests for the tool-call history rule require either extending `MockProvider` or constructing `Message`s manually with `reasoning_content` set and feeding them through `with_response`. `MockProvider::with_response` only takes a content string — needs a `with_reasoning_response(content, reasoning, tool_calls)` builder, or a generic `with_message(Message)` builder that takes the full message. The latter is cleaner and obviates the dual-purpose `with_tool_call_response`.
- **`Agent::stream` and `Agent::stream_owned` swallow reasoning when tools are present.** Lines 268–280 and 307–319 currently call `self.complete(messages).await` and yield only the final `response.content` as `TextDelta`. After SY-22, with tools + reasoning, the final `response.reasoning_content` must also be yielded as `ReasoningDelta` *before* `TextDelta` so that the renderer can place it above the answer. Streaming paths without tools (lines 257–264, 296–303) delegate directly to `provider.stream(...)`, which will already yield `ReasoningDelta` once `openai_compat::stream_sse` is updated.
- **Storage round-trip is partly tested today** but only for `tool_calls` (`test_sqlite_tool_calls_roundtrip`). Need a parallel `reasoning_content` round-trip test, plus a "legacy NULL → None" test (since the migration adds the column nullable to existing databases).
- **Telegram `<blockquote>` fits inside `TELEGRAM_MSG_LIMIT = 4096`.** When reasoning is long (V4 Pro can produce hundreds of tokens of CoT), the prepended blockquote can push the first chunk over the limit. PRD specifies `TELEGRAM_REASONING_PREVIEW_MAX_CHARS = 1500` with `synapse_core::text::truncate(reasoning, 1500)` and a `…[reasoning truncated]` suffix. The truncate helper appends `...` automatically when it cuts, so the `[reasoning truncated]` marker has to be appended **after** truncate and the limit chosen so total ≤ ~1500 chars before adding to the chunker. This is a detail for the plan, not a blocker.
- **`reasoning_effort` value space is unconstrained.** PRD §Constraints item 4: any string accepted; rely on API rejection. A typed enum (`enum ReasoningEffort { Low, Medium, High, Max }` with serde-rename) is a possible follow-up; out of scope for SY-22.
- **No backward "fix-up" of in-flight V4 Pro sessions.** Pre-existing rows have `NULL` `reasoning_content`; old rows that previously contained tool calls (against `deepseek-chat`) deserialize correctly to `None`. For users who happened to switch a session from `deepseek-chat` to `deepseek-v4-pro` mid-conversation and have tool-calling assistant turns in history without reasoning, the next API call with V4 Pro will work because the absent-`reasoning_content` is simply omitted (DeepSeek treats it as "no prior reasoning was retained" — text-only-style turn). This is acceptable.
- **CLI piped output (one-shot mode).** `synapse-cli/src/main.rs:129` writes `text` to stdout token by token. With reasoning enabled in CLI, mixing reasoning into stdout would break tools that pipe Synapse output (e.g. `synapse "give me X" | jq`). The plan should route `ReasoningDelta` to **stderr** in one-shot/non-TTY mode; in interactive REPL, render to the dim history pane. The PRD's `[cli] show_reasoning` toggle covers TTY mode; piped output should likely default to `false` regardless. **Flag for the plan as a small open detail** (no PRD update needed; the plan can decide).
- **Anthropic provider streams via a different module (`provider/anthropic.rs`).** Adding `StreamEvent::ReasoningDelta` does not affect Anthropic flows — Anthropic continues to yield only `TextDelta`. The `match` exhaustiveness has to be updated in any consumer that matches on `StreamEvent` (REPL, one-shot CLI, agent), but Anthropic's emit-path is unaffected. SY-23 will hook Anthropic's own thinking deltas into `ReasoningDelta` later.

## New Technical Questions

These surfaced during research and were not in the PRD. They are non-blocking — the plan can settle them — but the plan author should be aware:

1. **CLI one-shot mode reasoning handling.** Should `synapse-cli` (one-shot, non-TTY) route reasoning to stderr regardless of `[cli] show_reasoning`? My recommendation: yes (stderr by default; `[cli] show_reasoning = false` silences entirely). This keeps stdout clean for pipelines while preserving auditability. PRD only specifies REPL behavior; one-shot mode is implicit.
2. **`MockProvider` extension shape.** Two viable APIs: (a) a generic `with_message(Message)` that takes a fully-built message and replaces the dual-use `with_response`/`with_tool_call_response`, or (b) a third helper `with_reasoning_response(content, reasoning)`. (a) is cleaner; (b) is more conservative. Recommend (b) to avoid touching existing tests, and mark `with_response` as the simple-case helper.
3. **`Agent::stream*` path with tools: yield order.** When the final assistant message has both `reasoning_content` and `content`, what is the canonical yield order? My recommendation: yield all `ReasoningDelta` events first (chunked from the full reasoning string into a single delta is fine for now since `Agent::complete` returns the whole message at once when tools are involved), then a `TextDelta` for the final `content`, then `Done`. This gives REPL/Telegram a deterministic ordering for rendering above the answer.
4. **Where to store the reasoning preview cap constant?** `TELEGRAM_REASONING_PREVIEW_MAX_CHARS = 1500` could live in `handlers.rs` or in a sibling constants module. PRD specifies the value but not the location. Recommend `synapse-telegram/src/handlers.rs` near `ERROR_REPLY` for locality.
5. **CLI `[cli]` config section.** No precedent in the codebase (no existing CLI-only config section). The plan should decide whether to add `CliConfig { show_reasoning: bool }` with `pub cli: Option<CliConfig>` on `Config`, or to fold the flag into a more generic `[render]` section that can hold future CLI/Telegram-shared flags. Recommend the former (`[cli]`) because `telegram.show_reasoning` is symmetric and per-frontend.
6. **`StreamEvent` `#[non_exhaustive]`.** Should this attribute be added now to insulate against future variants (Anthropic thinking, OpenAI o-series reasoning)? Pro: future-proof; con: forces external `match`es to add a wildcard arm now. Recommend yes — pre-1.0 is the right time. PRD does not address this.
