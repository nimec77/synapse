# SY-22: DeepSeek V4 Pro Reasoning Model Support

Status: PRD_READY

## Context / Idea

**Arguments:** SY-22 (free-form description, no description file)

**User request:** "The new version of DeepSeek V4 Pro has been released — https://api-docs.deepseek.com/. We need to rework our project to support this model. It's a reasoning model, so its call format is different from how we called DeepSeek models before."

**Goal:** Make Synapse able to talk to DeepSeek V4 Pro's *thinking mode* (chain-of-thought reasoning) while keeping the existing non-reasoning DeepSeek models (`deepseek-chat`) working unchanged.

### What is different about a DeepSeek reasoning model

Sourced from DeepSeek's public docs (https://api-docs.deepseek.com/, /guides/thinking_mode):

1. **Model identifier**: `deepseek-v4-pro` (sent in the `model` field of `/chat/completions`).
2. **Two new request fields** must be sent when thinking mode is desired:
   - `thinking: { "type": "enabled" }` — top-level object that toggles thinking mode (the OpenAI Python SDK exposes this as `extra_body={"thinking": {"type": "enabled"}}`; over raw HTTP it is a real top-level field).
   - `reasoning_effort: "high" | "max"` (also documented as `"low" | "medium"` in the OpenAI ecosystem; DeepSeek docs explicitly mention `"high"` as the default and `"max"` for complex agent flows).
3. **Response format adds a sibling field** on the choice message:
   - `choices[0].message.reasoning_content` — the model's chain-of-thought.
   - `choices[0].message.content` — the final answer (unchanged).
4. **Streaming deltas add a sibling field** on the delta:
   - `choices[0].delta.reasoning_content` — incremental reasoning tokens.
   - `choices[0].delta.content` — incremental final-answer tokens (unchanged).
5. **Conversation history rules (CRITICAL):**
   - On a turn that produces **no tool calls**, `reasoning_content` is *optional* in subsequent context — it can be dropped.
   - On a turn that produces **tool calls**, the assistant's `reasoning_content` **MUST be passed back** to the API on every subsequent turn (DeepSeek docs: *"the intermediate `assistant`'s `reasoning_content` must participate in the context concatenation and must be passed back to the API in all subsequent user interaction turns"*).
6. **Unsupported sampling parameters** in thinking mode: `temperature`, `top_p`, `presence_penalty`, `frequency_penalty`. Synapse currently never sends these, so no breakage.
7. **Tool/function calling IS supported** in thinking mode — the existing tool-call machinery still applies.

### Why this is non-trivial in the current codebase

A scan of `synapse-core/src/provider/` reveals concrete impedance mismatches:

- **`Message` struct** (`synapse-core/src/message.rs:64`) has no `reasoning_content` field. With tool calls, we must store and replay it — there is currently nowhere to put it.
- **`OpenAiCompatProvider`** (`synapse-core/src/provider/openai_compat.rs:272`) hard-codes the request shape with no place for `thinking` or `reasoning_effort`. Both `DeepSeekProvider` and `OpenAiProvider` are thin wrappers over it (the SY-21 consolidation), so adding reasoning fields naively to the shared struct would leak DeepSeek-only fields into the OpenAI provider.
- **`ApiRequest` / `StreamingApiRequest`** (`synapse-core/src/provider/openai_compat/types.rs:29,47`) have no `thinking` or `reasoning_effort` fields, and `ApiMessage` (`types.rs:13`) has no `reasoning_content` field — so we cannot serialize the historical reasoning back to the API.
- **`ChoiceMessage` / `StreamDelta`** (`types.rs:108,146`) do not deserialize `reasoning_content`, so even if the API returned it we would silently discard it.
- **`StreamEvent`** (`synapse-core/src/provider/streaming.rs:23`) has only `TextDelta(String)` and `Done`. There is no way to surface reasoning tokens distinctly to the renderer — without a new variant, REPL/Telegram cannot tell reasoning apart from final answer.
- **`StoredMessage`** (`synapse-core/src/session.rs:83`) and the SQLite schema have no `reasoning_content` column. The codebase already has a precedent migration for adding tool columns (`migrations/20260208_002_add_tool_columns.sql`), so a `20260510_004_add_reasoning_content.sql` migration is the established pattern.
- **REPL renderer** (`synapse-cli/src/repl/render.rs`) and **Telegram renderer** (`synapse-telegram/src/handlers.rs`) currently treat any `TextDelta` as the user-visible answer. They will need to render reasoning differently (dim style in REPL, `<blockquote>` or hidden in Telegram).
- **`Agent`** (`synapse-core/src/agent.rs:194`) drives the tool-call loop and concatenates assistant responses into history. It must preserve `reasoning_content` on assistant messages whose `tool_calls` are non-empty (DeepSeek's hard requirement).
- **Factory** (`synapse-core/src/provider/factory.rs:46`) selects a provider purely by `config.provider`. With reasoning a per-model concern, model-name detection (or new config fields) must drive whether to send `thinking`/`reasoning_effort`.
- **Config** (`synapse-core/src/config.rs:39`) has no `reasoning_effort` field and no toggle for "show reasoning to the user".

## Goals

1. **Add a first-class reasoning channel to the core types** — extend `Message` with `reasoning_content: Option<String>`, extend `StreamEvent` with a `ReasoningDelta(String)` variant, extend `StoredMessage` and the SQLite schema (new migration) with a nullable `reasoning_content` column.
2. **Let DeepSeek V4 Pro be selected via configuration** — accept `model = "deepseek-v4-pro"` (and any other reasoning-capable DeepSeek model name) and a new `reasoning_effort` config field (default `"high"`). Existing `deepseek-chat` configs must continue to work bit-for-bit identically.
3. **Auto-escalate effort to `"max"` when MCP tools are configured** — if `config.mcp.config_path` is set AND the user did not set `reasoning_effort` explicitly, the agent uses `"max"` instead of `"high"` (mirroring documented behaviour of Claude Code / OpenCode against DeepSeek). Explicit user values are always honoured.
4. **Send `thinking` and `reasoning_effort` only when the configured DeepSeek model is reasoning-capable** — never leak these fields to non-reasoning DeepSeek models or to the OpenAI provider.
5. **Parse `reasoning_content` from non-streaming responses** and from streaming deltas, route reasoning tokens via `StreamEvent::ReasoningDelta`, and store the final reasoning on the assistant `Message`.
6. **Honour the tool-call history rule** — when an assistant message has `tool_calls.is_some()` AND `reasoning_content.is_some()`, the next API call must include both fields on that historical assistant turn. On text-only turns, drop `reasoning_content` from outbound history (DeepSeek-spec exact; saves tokens). No config flag — this is the fixed policy for SY-22.
7. **Render reasoning distinctly to humans** — in the REPL, show reasoning in a dim style by default (CLI is developer-facing; visibility helps audit). In Telegram, hide reasoning by default (privacy: messages can be screenshotted/forwarded); enable display via `telegram.show_reasoning = true` in `config.toml`. There is no `/reasoning` runtime toggle in SY-22.
8. **Persist reasoning across sessions** — `reasoning_content` round-trips through SQLite so a resumed session that contained tool calls still satisfies DeepSeek's history rule.
9. **Documentation and examples** — update `CLAUDE.md`, `README.md`, `config.toml.example`, and add a brief `docs/research/SY-22-deepseek-v4-pro.md` capturing the wire-format details so future contributors do not have to re-derive them.

Non-goals (explicitly out of scope):

- **Anthropic extended thinking** (`thinking: { type: "enabled", budget_tokens: N }` on Claude Sonnet 3.7+). Same conceptual feature, different wire shape — defer to a follow-up ticket.
- **OpenAI o-series reasoning** (`reasoning.effort` field on o1/o3). Defer to a follow-up.
- **Surfacing reasoning into MCP tool inputs.** Reasoning is a debugging/UX concern; tool inputs come from `tool_calls`.
- **Token budgeting or hard cap on reasoning length.** DeepSeek does not document a separate budget; we will treat `max_tokens` as covering the combined output and revisit if practice shows otherwise.

## User Stories

1. **As a user**, I can set `model = "deepseek-v4-pro"` in `config.toml` and use Synapse exactly as before, but with chain-of-thought reasoning improving response quality.
2. **As a user**, I can configure `reasoning_effort = "max"` for harder agentic tasks and `"high"` (the default) for normal use.
3. **As a CLI user**, I see the model's reasoning streamed in a dim/collapsed style above the final answer, so I can audit how the model thought without the reasoning drowning out the answer.
4. **As a Telegram user**, by default the bot sends only the final answer; if I enable a `show_reasoning` flag, the bot wraps the reasoning in `<blockquote>` above the answer.
5. **As a contributor**, the existing `deepseek-chat` model continues to work without sending any new fields, so non-reasoning users see zero behavior change.
6. **As a user using MCP tools with V4 Pro**, multi-turn tool conversations succeed because the agent automatically replays the assistant's `reasoning_content` on tool-using turns (without me having to know about that protocol detail).
7. **As a user resuming a session**, a resumed conversation that previously used tool calls with V4 Pro continues to work because `reasoning_content` was persisted to SQLite and is replayed on the next API call.

## Constraints and Assumptions

1. **Backwards compatibility is mandatory** — existing configs that target `deepseek-chat`, `claude-*`, or any OpenAI model must produce byte-identical request bodies after this ticket. The new request fields are *only* serialized when the resolved provider has `reasoning: Some(_)`.
2. **The OpenAI provider must NOT send `thinking`/`reasoning_effort`** — `OpenAiProvider::new` does not pass `ReasoningSettings`, so its `OpenAiCompatProvider.reasoning` stays `None` and the `Option` fields stay omitted via `skip_serializing_if`.
3. **Anthropic provider is untouched** in this ticket (uses a different module entirely).
4. **`reasoning_effort` valid values are not strictly enforced** at the type level — DeepSeek docs explicitly mention `"high"` and `"max"`, and the OpenAI ecosystem also defines `"low"` and `"medium"`. We accept any string and let the API reject invalid values. (A typed enum can be added in a follow-up if desired.)
5. **`max_tokens` semantics for reasoning models are not formally documented**. We assume `max_tokens` covers the combined output (reasoning + answer) — the existing default of 4096 may be too low for "max" effort. This is an explicit open question (see below).
6. **No retroactive backfill of `reasoning_content`** for already-stored messages — old rows have `NULL`, which deserializes to `None`, which is correct (those turns predate reasoning).
7. **Pre-commit gate after every task**: `cargo fmt --check && cargo clippy -- -D warnings && cargo test`.
8. **No new `mod.rs` files** — follow Rust 2018+ module convention.
9. **No `unwrap()`/`expect()` in `synapse-core`** — `?` propagation only.
10. **Char-safe handling of reasoning text** — reuse `synapse_core::text::truncate` for any preview/log output of reasoning to avoid UTF-8 boundary panics (continuation of SY-21).
11. **Task ordering**: 22.1 (core types) and 22.2 (wire format) must precede 22.3 (factory). 22.4 (agent loop) and 22.5 (storage) depend on 22.1. 22.6 (REPL) and 22.7 (Telegram) depend on 22.2 and 22.5. 22.8 (docs) is last.
12. **Pre-1.0 semver**: this is a feature addition with no breaking external behavior — qualifies for a `minor` bump (`/release minor`) at the end.

## Decisions (resolved)

These were decided during PRD review:

1. **`reasoning_effort` auto-escalation** — Auto-escalate to `"max"` when MCP tools are configured AND the user did not set `reasoning_effort` explicitly. Explicit values always win. Encoded in Scenario 22.3 step 3.
2. **History policy for `reasoning_content`** — Drop on text-only turns; keep on tool-call turns. This is DeepSeek-spec-exact. No config knob in SY-22. Encoded in Goal 6 and Scenario 22.2.
3. **Default visibility** — CLI: show reasoning by default (`cli.show_reasoning = true`). Telegram: hide by default (`telegram.show_reasoning = false`). Encoded in Scenarios 22.6 / 22.7.
4. **Telegram `/reasoning` command** — Not in SY-22. Visibility is `config.toml`-driven only. Per-chat runtime toggling (with persistence) deferred to a follow-up ticket. Encoded in Scenario 22.7 step 4.

## Remaining Open Questions (deferred / non-blocking)

These do not block implementation; defaults are documented in the PRD.

1. **`max_tokens` floor for `"max"` effort** — should we automatically raise `max_tokens` to e.g. 16384 when `reasoning_effort = "max"` and the configured value is below 8192? Defaulting to *document the recommendation only*. Revisit if practice shows truncation is common.
